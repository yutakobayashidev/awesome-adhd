# STTと神経多様性支援

音声認識（STT: Speech-to-Text）を ADHD、ディスレクシア、自閉スペクトラムといった神経多様性の支援に使う際の設計指針と実証的知見を整理する。

## 核心

神経多様性支援において重要なのは「最高精度のASR」ではない。**記録の再生可能性、検索可能性、速度変更、正確なキャプション、ノイズ下での可用性、そしてタスクや要点を後から構造化できること**が実用的価値を持つ。録画講義と検索可能な transcript は、ADHD 学生の学習ペース自己調整を助け、一般学生にも復習資源として有用だが、不正確な字幕や同期ずれは神経多様な学習者の認知負荷を上げる。したがって支援用途では、「低遅延」より「信頼できる精度」「再編集可能性」「ユーザー確認可能な構造化」が優先される。

## ADHD

録画講義を用いた学習により、学習の pace・place・time を自分で制御できる感覚が得られたことが質的研究で示されている。STT 単体の効果ではないが、**録音と検索可能な transcript によって、聞き逃しや集中の揺れを後から補完できる**点が重要。また、ADHD の不注意症状が高いほど手書きよりタイピングのほうが講義学習に有利になる傾向も報告されており、音声→構造化ノートへの変換はこの流れと整合的である。

## ディスレクシア

STT を用いた文章産出支援が、単語・文・テキスト品質を改善したという 2024年の単一事例研究がある。高等教育におけるディスレクシア学生の講義ノート作成困難は、**処理・保持・検索の困難と時間制約が重なる**点に起因する。このため、「生音声の完璧な逐語転写」より、**聞きながら全部書こうとさせないこと**と、**後から検索・再配置・再編集できること**の価値が大きい。

## 自閉スペクトラム

オンライン学習の認知負荷研究では、オーディオに加えて文字が提供されることが一部の自閉スペクトラム学生に有益でありうる一方、**不正確な transcript や同期の悪い caption は認知負荷を上げる**と指摘されている。実用性を左右するのは STT の導入自体ではなく、**字幕品質・同期精度・表示の柔軟性**である。text を出すだけでは不十分で、誤りが少なくペース変更や表示切替が可能であることが条件になる。

## 会議・構造化タスク支援

会議 transcript から action item を検出する研究は古くからあり、近年は action-item-driven summarization が一般的な要約よりタスク中心の要約を改善する方向で進んでいる。長い会議 transcript を区分し action item 抽出を組み込むことで、AMI コーパス上の BERTScore が改善されたとの報告がある（2023–2024年）。つまり、**STT を会議メモに使うだけなら transcript で十分だが、実務価値を出すには「誰が・何を・いつまでに」を抽出する第2段階が必要**である。

医療や高負荷な対話では、**ASR 誤りが下流要約を劣化させる**ことも確認されている（2024年研究）。ASR ノイズ率が高まるほど医療対話の要約品質が低下し、逆に ASR ノイズを考慮した訓練が要約モデルの頑健性を改善する。このことから、支援アプリでは「低信頼箇所を可視化し、ユーザー確認を必須化」することが、認知負荷と混乱の防止に直結する。

## 実装アーキテクチャ

支援に適したアーキテクチャは、単一ベンダーに委ねるより、**4層に分離する設計**が堅実である：

1. **入力層** — ローカル VAD と push-to-talk / hold-to-talk で不要な長尺録音を減らす
2. **転写層** — 端末ローカル STT を第一候補にし、必要時のみクラウド高精度モデルへフォールバック
3. **構造化層** — 段落化、話者分離、要点抽出、action item 抽出
4. **行動化層** — ToDo・カレンダー・ノートアプリ・学習カードへ出力

この分離により、リアルタイム性が必要な場面（低遅延字幕）と、高精度要約が必要な場面（後処理構造化）を切り分けられる。

### Confidence-Aware UI

ASR には常に誤りがあり、誤った transcript をそのまま「正解」として出すことは神経多様性支援では認知負荷と混乱の増幅につながる。支援用 UI には最低限以下が必要：

- **低信頼語のハイライト**
- **ワンタップ修正**
- **固有名詞辞書**
- **短いセグメント単位での再実行**
- **要約前の人間確認**

### データガバナンス

データ分類に応じた経路分離を最初から設計する：

- **低リスク** → クラウド直送
- **中リスク** → 端末前処理 + redaction + クラウド要約
- **高リスク** → 完全ローカル / コンテナ / オンプレ

## 推奨方針

**支援ワークフローは local-first、summary/task extraction は consented cloud or private deployment、最終アクション確定は human-in-the-loop** が最も堅実である。

### 利用シナリオ別の推奨

- **個人利用** → Superwhisper または Handy のようなローカル系をベースにし、要約だけ必要時クラウド化
- **開発・プロンプト入力中心** → Aqua Voice のような cloud dictation は強力だが、PII の扱いには追加確認が必要
- **企業の本番システム** → Google / Azure / AWS の統制機能、または Deepgram / AssemblyAI の音声特化 API を選び、会議要約・タスク抽出・学習支援 UI を自社実装
- **神経多様性支援** → [[genio-notes|Genio Notes]] 型の「録る→見返す→切り出す→再整理する」UX を参考に、字幕品質監視とユーザーの選択肢を中心に据える
